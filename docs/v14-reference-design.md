## 2. 逐项验算

### 2.1 中文点阵字库（这是本需求最大的一笔开销）

整个设计需要 **52 个不同字符**：

```
16×16 全宽（51 个）：
一七三九二五八六冬分初十卅后周四处夏大天寒小年廿惊日明星春暑月期正水清满白秋种立腊至芒种谷闰降雨雪霜露

8×16 半宽（1 个）：℃
```

| 项 | 计算 | 体积 |
|---|---|---|
| 点阵数据 | 51 × 32 B | 1632 B |
| 字形索引表 | 51 × 7 B | 357 B |
| 字符映射表 | 51 × 2 B | 102 B |
| **合计** | | **2091 B（2.0 KB）** |

**许可已确认**：GNU Unifont 自 13.0.04 版起**双重授权** ——
GPL-2.0-or-later 附 Font-exception-2.0，以及 **SIL OFL 1.1**。
两者都明确允许把字形嵌入程序而不使程序受传染。选 OFL 1.1 即可，已在 LICENSE 中注明即可。

> 备选：文泉驿点阵正黑（GPL+字体例外）。但从 15.1.05 的 Unifont 直接取子集最省事，
> 且点阵是原生 16×16，不需要栅格化，不会发虚。

### 2.2 第一行宽度预算

度量口径与固件一致：ASCII 每字符 8 px、汉字每字符 16 px（= `obdWriteStringCustom` 的 xAdvance）。

| 串 | 宽度 | 余量 | 判定 |
|---|---|---|---|
| `2026年7月21日 星期二 31℃` | 192 px | 58 px | ✅ |
| `2026年7月21日 星期二 -10℃` | 200 px | 50 px | ✅ |
| `2026年12月31日 星期日 31℃` | 208 px | 42 px | ✅ 最宽合法串 |
| `2026年12月31日 星期日 -10℃` | 208 px | 42 px | ✅ |
| `2026年12月31日 星期日 -10℃ 2905mV` | **264 px** | **−14 px** | ❌ 溢出 |
| `2026年12月31日 星期日 -10℃2905mV` | **256 px** | **−6 px** | ❌ 溢出 |

**这组数字解释了一件事**：参考图为什么用电池图标而不是电压数字 ——
日期全称 + 负温度 + 电压，三者一起就放不下了。这不是设计者的偏好，是宽度逼出来的。

### 2.3 第二行 大时钟（本次唯一的硬技术点）

参考图实测：**高 68 px，宽 187 px**（占屏宽 75%）。

机器上现成的字体是 `DSEG14_Classic_Mini_Regular_40`，它的宽高比是 **0.85**：

| 方案 | 计算 | 结果 |
|---|---|---|
| 现有字体等比放大到 68 px | 68 × 0.85 = 57.8 px/字 × 5 = **289 px** | ❌ 超宽 39 px |
| 现有字体等比放大到「塞得下」为止 | 每字 46.8 px → 高度封顶 **55.1 px** | 比参考图矮 19% |
| **手绘 7 段码，宽高比自定 0.59** | 68 px 高 → 「14:36」总宽 **187 px** | ✅ 与参考图完全一致 |

所以时钟不能靠现成字体，要**用几何画**。这里有个副产品：

> 删掉 `DSEG14_Classic_Mini_Regular_40` 能省 **8800 B**（bitmaps 8135 B + 字形表 665 B），
> 比新增的中文字库（2091 B）还多。**Flash 因此净减。**

7 段几何参数（已用样张验证外观）：字高 68、字宽 40、段厚 8、斜角 4、字符间距 8；
`1` 用 0.55 倍窄宽（参考图的 `1` 明显比 `9` 窄）。

### 2.4 农历

用通行的 1900–2100 `lunarInfo` 表（4 B/年）：

- 表体积 **804 B**
- 算法：与公历基准日差 → 逐年递减 → 定位月/日，纯整数运算，无浮点

已交叉验证：

| 公历 | 农历 | 说明 |
|---|---|---|
| 2026-02-17 | 正月初一 | 春节 ✓ |
| 2026-09-11 | 八月初一 | ✓ |
| 2026-09-12 | 八月初二 | ✓ 样张用这一天 |
| 2026-09-24 | 八月十四 | ✓ |

### 2.5 节气

**不能用常见公式**。用 Meeus 天文算法离线核过 2026 全年 24 个节气，
发现「寿星公式」在 **2026 年芒种** 上会算成 6月6日，实际是 **6月5日 23:48** —— 差一天。

因此采用**离线用天文算法生成、固件里查表**的方式：

| 覆盖范围 | 体积 | 判定 |
|---|---|---|
| 2026–2050（25 年） | **600 B** | ✅ 推荐 |
| 2020–2050（31 年） | 744 B | ✅ |
| 1900–2100（201 年） | 4824 B | ✅ 也放得下 |

只存「日号」（1 字节/项），月份是固定的。超出范围的年份优雅降级：只显示农历、不显示节气。

显示逻辑（已验证）：与下一个节气相差 N 天 → `N天后XX`；当天 → `今日XX`。

样张用的是真实数据：2026-09-12 的下一个节气是秋分（9/23），**11 天后**。

### 2.6 蓝牙名

设备名的产生位置已经找到：`ble.c:39` 定义 `ble_name[]`，`ble.c:112-117` 用 MAC 低 3 字节填进去：

```c
bls_ll_setScanRspData((uint8_t *)ble_name, sizeof(ble_name));
// -> "ESL_" + MAC[2] MAC[1] MAC[0] 的十六进制，例如 ESL_1A2B3C
```

参考图的 `[881A]` 就是这个名字的**后 4 位**。取 `ble_name[8..11]` 即可，不需要新增任何存储。

> 注意：屏幕上现在那行 `ESL_140EC6 BWR213` 是 `epd.c:451` 自己拼的字符串，
> 跟广播名是两回事。名字必须从 `ble_name[]` 取，才能和手机搜到的设备一致。

### 2.7 Flash 预算

固件区 `0x00000–0x1FFFF`（128 KB），v13.0 镜像 91260 B，余 38912 B。

| 增加 | 体积 |
|---|---|
| 中文点阵字库 | +2091 B |
| lunarInfo 表 | +804 B |
| 节气查表 | +600 B |
| 渲染 + 历法代码 | +约 1200 B |
| **小计** | **+4695 B** |
| **删除** `DSEG14_Classic_Mini_Regular_40` | **−8800 B** |
| **净变化** | **−4105 B** |

预计镜像 ≈ **87155 B**，剩余 ≈ **43.9 KB**。**没有任何 Flash 压力。**

### 3.1 第一行末尾：电压数字，还是电池图标？

| 方案 | 效果 | 代价 |

- 全称「星期二」：多占 16 px，参考图用的这个
- 简称「周二」：省 16 px，为上面的方案 B 腾出空间

建议 2026–2050。超出后自动只显示农历。如果你想要更长（比如到 2100），也只多占 4 KB。

## 4. 风险与对策

### 4.1 SRAM —— 这是唯一真正需要小心的地方

`epd_display()` 带 `_attribute_ram_code_`，函数体会被复制进 RAM 执行。
往里塞农历/节气/中文排版逻辑，**每多一条指令都吃 SRAM**，而当前只剩 **4175 B**
（`_end_bss_ = 0x84efb1`，栈顶 `0x850000`）。溢出不会报错，**上电即砖**。

对策（会严格执行）：
1. 历法计算、字符串格式化全部放**普通函数**（非 `ram_code`），`epd_display()` 只做绘制调用；
2. 编译后必查 `_end_bss_ < 0x850000`，并和 v13.0 的 `0x84efb1` 对比增量；
3. 增量超过 1 KB 就停下来重新分配。

### 4.2 手绘段码是首次实现

参考图的段码形状需要按几何画，不是现成字库。风险是**画出来不好看**。
对策：先在离线脚本里调好参数（已完成，见样张），再把同一组几何原样搬到 C，
保证「脚本里看到的」就是「屏上出现的」。

### 4.3 不动数据通路（沿用老规矩）

新内容仍然走 `obdSetPixel → epd_temp → FixBuffer → EPD_Display`，一行都不改。
最坏情况是「画得不对」，不会是「花屏或刷不干净」。

## 7. 对账：预测 vs 交付

| 项目 | 本文预测 | 实际交付 | 结论 |
|---|---|---|---|
| Flash | 净减 4405 B → 镜像 ≈ 87155 B | 91260 → **82460 B（净减 8800 B）** | **比预测还好 4.4 KB**：预测只算了「删 DSEG14」，实际 `Dialog_plain_16` 与 `Special_Elite_Regular_30` 也一并被 `gc-sections` 裁掉 |
| 中文字库 | 2091 B | 2522 B（79 字形，含符文） | 多了 `℃` 等半宽字形与索引表 |
| 节气表 | 600 B | 624 B | 多了一年前瞻行，见下 |
| SRAM | 余 4175 B，`_end_bss_ = 0x84efb1` | `_end_bss_ = 0x84efa1`，**余 4191 B** | 历法与排版全在 Flash 执行，SRAM 反而降了 16 B。⚠ 本文 §4.1 把余量写成 4175 B 时算错了 16（0x850000−0x84efb1 = 4191），以实测为准 |
| 局部刷新窗口 | 未讨论 | **137 → 92 栅极（46% → 31%）** | 本文完全没预见到：见 §7.1 |
| 大时钟 | 手绘 h68/w40/厚8/斜4/距8 = 187 px | 一致 | ✅ 脚本里的几何原样搬进 C |

### 7.1 三件本文没想到、在实现中才暴露的事

1. **局部刷新窗口要求「数字占固定槽位」。** 最初按串宽居中排时钟，这看起来只是审美
   问题 —— 直到把「枚举全部 1440 个 HH:MM、逐拍 diff 帧缓冲」跑出来：`1` 进出分钟位
   会让整串变窄并重新居中，于是**小时数字也跟着平移**，实际变化的列是整个时钟
   （玻璃 x 18..231），窗口必须覆盖 214 列。改成固定槽位后并集缩到 140..231，
   窗口 92 门。**一个排版选择直接把省电预算翻了一倍。**

2. **栅极窗口是竖直带，会连带重画行 1。** 窗口按栅极线驱动，带内所有行都被重写。
   行 1 的 `31℃ 2905mV` 恰好落在 x 140..231 带内，所以电压读数必须逐分钟稳定 ——
   `app.c` 因此在整点全刷时给 `shown_mv` / `shown_temp` 拍快照，局部刷新期间一直显示
   快照值。否则末位漂移会被每分钟重绘，9→10 的宽度变化还会留下错位残影。

3. **节气表需要一年前瞻。** `next_term()` 是向前扫的，2050-12-23 之后要跨进 2051 才能
   找到下一个节气，否则那 9 天没有节气可显示。表因此是 26 年而不是 25 年
   （`CAL_TERM_YEAR_FIRST 2026` / `CAL_TERM_YEAR_LAST 2051`）。

### 7.2 实现中发现并修掉的真 bug

| bug | 后果 | 怎么发现的 |
|---|---|---|
| `xr = x1 - t + 1`（数字右竖条） | 右边缘落在 `x+w`，墨迹出了窗口推导所依据的格子，窗口必须多 1 门才不残影 | 把 `column_bits` 从「只扫格子宽」改成**全宽扫描**才现形 —— 原来的写法直接把越界墨迹丢掉 |
| 行 1 缓冲 `uint16_t r1[24]` | 最宽串需 26 字符 + NUL，越界写 3 个 `uint16_t` 进调用者栈帧 | 穷举公历全范围 × 温度/电压量程端点求最宽串 |
| 符文空读（镜像侧） | 预览里符文位整块空白 | 预览图；根因是镜像的 `uf_blit` 硬编码读字体数组，而固件传的是 `BLE_RUNE_BITS` |
| 符文缺左下臂 | 字形偏斜、左下沉 | 重看用户手绘草图，左下有**独立一笔**，与「上臂共线于下弦」的假设矛盾。改为上下对称的左向箭头，并加了一条**镜像对称断言**把它钉住 |
| 验证器自身 4 处缺陷 | 闰月检查拿公历年比农历年（"通过"是巧合）；否定性测试用了非最宽串；格子宽度取错索引 | 逐条复核断言「真的能失败吗」时发现 |

> **一句话**：本文 §2 的宽度/体积验算基本靠谱，§4 的风险判断（SRAM 是唯一真风险）
> 也对 —— 但它漏掉了整件事里**收益最大**的那一条：版面本身决定了局部刷新的窗口大小。
